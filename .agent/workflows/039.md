# [Workflow-039] 現在の変更差分(Diff)を分析し、リファクタリング計画を策定するワークフロー (Analyze Diff & Reformulate Plan)

## 概要

作業の再開時や、ユーザーが手動でコードを修正した際、現在の作業ディレクトリの状態（Diff/Status）を正しく把握し、それを既存の計画書（`implementation_plan.md` 等）や今後のタスクに同期させるための手順です。

## 課題 (Problem)

1.  **計画の乖離**: ユーザーの手動修正や、中断前の未完了作業が存在する状態で作業を続行すると、AI が古い前提でコードを生成し、デグレードやコンフリクトを引き起こす。
2.  **不透明な意図**: ユーザーによる「意図的なリファクタリング」を AI がバグと誤認して元に戻してしまうリスクがある。

## 手順 (Step-by-Step)

### 1. 変更状況の把握

- `git status` を実行し、変更されたファイルの一覧を確認します。
- `git diff`（未ステージング）および `git diff --cached`（ステージング済み）を実行し、具体的なコード変更を取得します。

### 2. 変更の分析とリスペクト

- **網羅的な分析**: AI 自身の変更かユーザーの変更かを問わず、すべての Diff を分析対象とします。
- **意図の推測**: ユーザーの手動変更が含まれる場合、その意図（例: [Workflow-008] の適用、コンポーネントの共通化など）をコードから読み取り、高く評価（リスペクト）します。
- **不整合の特定**: 既存の `implementation_plan.md` やタスクリストと矛盾している箇所がないか、あるいは追加で必要なリファクタリングがないかを洗い出します。

### 3. 計画への同期（再策定）

- **計画書の更新**: 現在の Diff の状態を「実装済み」または「ベースライン」として `implementation_plan.md` を更新します。
- **追加タスクの定義**: ユーザーの変更によって必要になった追随作業（例: 他のコンポーネントへの波及、型定義の修正）をタスクリストに追加します。
- **DoD の再定義**: 修正箇所が増えた場合、それに応じた検証手順（Build/Typecheck 等）を計画に含めます。

### 4. ユーザーへの合意形成

- 分析結果（「～のような変更を確認しました。これを踏まえ、計画を～のように更新します」）を提示し、承認（Atomic Approval）を得ます。
